## 用户已确认需求（2026-10-17，场景访谈结果）

本节为用户逐题确认的需求，优先于下方历史访谈选项；确认需求不等于授权实施。本轮仅整理文档，未修改时间分类、业务代码、数据库或通知服务。

### 想从记录中得到什么

- 重点是看清学习过程中哪里耗掉了时间，以及一天的时间去了哪里；用户最初选B、C，随后明确纠正：A“只看真正学了多久”没有什么优先级。不能据此把有效学习总时长作为唯一产品重点。
- 主动休息与忍不住刷手机要明确区别；必须接的电话属于外部打断，与主动休息、分心分别看。
- 点“吃饭”后结束当前学习段，开始记录吃饭时间，不只是停止后留下未记录空档。吃饭记录是否挂在原数学任务下，还是归入当天独立活动实体，尚未单独确认，不能把记录时间段的选择当作数据结构授权。

### 学习有效率的明确口径

有效率＝有效学习时间÷（有效学习时间＋分心时间）。吃饭、主动休息和外部打断各自记录时长，不进入学习有效率分母；不把所有非学习都当成分心。

| 用户确认的场景 | 应展示的结果 |
| --- | --- |
| 学习60、分心刷手机20、吃饭30分钟 | 学习时段有效率75%；吃饭30分钟单列 |
| 认真学习60、主动休息10分钟，没有分心 | 有效率100%；主动休息10分钟单列 |
| 认真学习60、必须接的电话打断15分钟，没有分心 | 有效率100%；外部打断15分钟单列 |

用户在60／20／30场景选择75%，没有选择60÷110约55%的已记录时间学习占比。全天去向需要看各类时长，不据此将不完整记录称为全天覆盖。分母为0时如何显示、其他活动具体归类与历史记录如何兼容尚待设计，不在本轮擅自改动。

### 第一条通知的明确范围

- 优先场景：吃饭或休息达到自己设定的时长，提醒回来学习。连续学习提醒休息、当天目标达成、疑似忘停均不抢先作为第一条通知。
- 接收设备：Android手机。用户明确要求尽可能在锁屏、使用其他应用、没有看网站时也收到；这是需要实机验证的核心需求，不以网页内弹层代替。
- 内容示例：“吃饭／休息时间到了，该回来学习了。”这只是表达提醒意图，不是已确认的固定文案。
- 开始吃饭记录时，每次弹出选择，由用户决定是否提醒、多久后提醒。不能默认每次必开、沿用上次时长或强制固定30分钟；30分钟仅是访谈示例。
- 到点只提醒，原吃饭／休息计时继续，由用户回来后手动切换；第一版不自动停止、截断记录或因未响应而判定已经回来。
- 对主动休息是否完全复用吃饭的每次选择流程，以及通知点击动作、重复／补发、免打扰、具体传送通道仍未单独确认。ntfy是候选，用户没有确认手机已安装、已订阅或权限已开启。

- 已确认业务目标与第一条通知场景；本轮没有接入、发送、安装或部署通知，没有运行新的业务测试。
- 下一步可以基于本节准备实施方案；先核实手机通知通道和权限，在隔离环境验证锁屏／后台／换网送达，再按用户实际授权实施。先保留当前分类与所有既有未提交工作。

## 二、通知工具分别能做什么

| 方式 | 用在本项目上的作用 | 当前判断 |
| --- | --- | --- |
| 页面文字、弹层、声音 | 页面打开时提示“这段已到时间” | 适合作为补充；手机后台可能暂停页面，不能独自承担锁屏提醒 |
| 浏览器系统通知／Web Push | 在系统通知栏显示消息，Web Push可由服务器唤起Service Worker | 可以保留网页；需要订阅与权限，可靠性受浏览器、网络和系统限制 |
| ntfy | 服务器发布消息，手机订阅后显示系统通知 | 用户已有接触，值得优先评估；尚未确认手机的实际配置 |
| Syncthing／Syncthing-Fork | 在设备之间同步文件 | 不作为计时提醒通道；同步事件提示不等于可供业务直接使用的通用推送 |
| Tailscale | 设备与服务器之间的私有网络连接 | 服务器已运行；能承载连接，但本身不是本项目的到点通知服务 |
| 阿里云 | 网页关闭后继续判断提醒时间并发送消息 | 已有长期运行服务，可承载提醒后端；目前提醒功能尚未实现 |
| 原生App／桌面程序 | 可进一步接入本机能力、离线操作与系统入口 | 仅为到点通知暂不足以决定重写；可在明确离线与系统能力需求后再评估 |

推荐先验证的结构：

```text
网页开始一段计时
       ↓
阿里云保存这段计时与提醒时刻
       ↓ 到点且这段仍在运行
通知通道（优先评估ntfy）
       ↓
手机通知栏：“已学习45分钟，要休息一下吗？”
       ↓ 点开
回到当前执行页
```

上面45分钟只是示例，不是默认规则。点击通知先打开页面即可；是否需要通知栏直接停止／延长，应另行确认。

注意的实际条件：

- Android的ntfy自托管订阅通常使用即时投递的前台服务；需要手机允许通知及必要的后台运行。官方说明关闭即时投递会有明显延迟风险，不能承诺每台手机准点必达。
- 公共ntfy与自托管ntfy是不同部署选择。自托管应配置认证与主题权限，不能把学习信息发到随意可读写的公共主题；现阶段未创建任何主题或令牌。
- iOS／iPadOS自16.4起支持添加到主屏幕的网页申请Web Push权限；普通网页弹出通知的条件与Android不同。用户具体系统尚待确认。
- 到点后提醒仍需检查当前激活段；停止／切换后旧提醒应失效，多个页面不能重复发送。服务重启、临时断网后的迟到提醒如何处理属于后续设计。
- 通知是尽力送达；“后端已发送”和“手机已显示”是两个状态，最终需做实体锁屏、后台和换网验证。

## 三、当前时间分类究竟是什么

当前三类都可以计时，都能保存时间段：

| 分类 | 默认例子 | 算学习有效时间 | 算当前的“总投入” | 展示明细 |
| --- | --- | --- | --- | --- |
| 有效时间 | 数学网课、刷题 | 是 | 是 | 是 |
| 计总标签 | 上厕所、走动、打游戏 | 否 | 是 | 是 |
| 中断标签 | 吃饭、突发、手动暂停 | 否 | 否 | 是 |

这些是源码默认值，不代表用户当前设置，也不代表本轮认可这些归类。

例如：学习60分钟、游戏20分钟、吃饭30分钟。

- 当前有效时间：60分钟。
- 当前总投入：80分钟，包含游戏，不包含吃饭。
- 当前有效率：60÷80＝75%。
- 实际被这些记录覆盖的时间：110分钟；它不是目前的“总投入”。

因此，“中断不计入”指不进入当前总投入与有效率分母，并非不记录时长。停止后没有激活段的空档，才没有被持续记录。当前中断还挂在切入前的任务下，不是独立的全天生活时间池。

当前结构能表达“学习时段内的低效／分心”与“离开学习时段的休息／事务”，但仅凭默认标签无法确认这就是用户原始目的。尤其“打游戏算投入、吃饭不算”需要重新讨论，不把解释当成历史事实。

## 四、历史访谈清单（实际回答见顶部确认结果）

先从场景提问，不要求用户先理解统计名词；建议一次只聊一个问题。

### 1. 晚上打开记录，你最想知道什么？

- A：今天真正学了多久，学到了哪里；非学习只需简单备注。
- B：为了学这60分钟，一共占用了多久，哪里被打断／分心。
- C：一天时间去了哪里，吃饭、休息、游戏也想单独看。

可以组合，但请先选最重要的一项。B偏向学习时段分析；C需要生活活动视角，不能直接等同于当前“总投入”。

### 2. 同样是非学习，你希望怎样看这几个例子？

逐个问：计划吃饭30分钟、学累了休息10分钟、忍不住刷手机20分钟、被电话打断15分钟。

- A：都记录，但学习以外只分活动名称，不再区分计总／中断。
- B：区分计划休息、分心、外部事务；统计上可各自看。
- C：只记录会影响学习判断的部分，其余停止即可。

不要预设吃饭／休息属于“低效”，也不要因为名称相近就全部塞入同一分母。

### 3. 点“吃饭”之后，你真正希望发生什么？

- A：停止学习，开始一段独立的吃饭记录，回来一键继续学习。
- B：只暂停学习，吃饭本身不用记录时长。
- C：记录吃饭，并在自己设定的时间后提醒回来。

A和C可组合。再确认该记录应留在数学任务里，还是作为当天独立活动。

### 4. 用具体数字确认“有效率”有没有用

同样是学习60、游戏20、吃饭30分钟：

- A：主要显示“有效学习60分钟”，先不显示比例。
- B：想看60÷80＝75%，吃饭不影响学习效率，游戏算分心。
- C：想看60÷110≈55%的已记录时间占比，同时分别解释生活与分心；不直接把它命名为学习效率。

如果主要诉求是找到分心原因，可以显示分心分钟，无须强求一个比例。若统计全天占比，还需明确未记录空档与睡眠，不能拿不完整记录冒充全天。

### 5. 第一条通知最值得解决哪个时刻？

- A：连续学到自己设定的时长，提醒休息。
- B：吃饭／休息到自己设定的时长，提醒回来。
- C：某科今天累计有效时间达到目标。
- D：疑似忘停或很久没回来，提醒核对。

随后确认：先提醒手机还是电脑；Android还是iPhone；已有ntfy应用／订阅是否仍可用；锁屏时是否也必须收到。先选一个场景和一个接收设备做最小验证。

### 6. 到点只提醒，还是改变计时？

- A：只提醒，计时继续，自己决定停止／延长（建议作为第一版起点）。
- B：自己事先选择到点自动停止。
- C：提醒提供“再延长一下”或“返回学习”的操作。

不因提醒未响应就自动截掉真实记录。后续再讨论重复提醒、免打扰、错过通知和长期离线。
